## 1 ИНСПЕКЦИЯ ПРОЕКТА ПО ПРИЗНАКАМ ТЕХНИЧЕСКОГО ДОЛГА
В ходе аудита кода проекта "Конфигуратор ПК" (Spring Boot REST API для конфигуратора ПК) был проведён анализ признакам технического долг.

### 1.1 Непонятный / нечитабельный код
– **Минимален**. Код соответствует стандартам Spring Boot: понятные имена пакетов и классов, constructor injection, использование Lombok и MapStruct. Методы в контроллерах и сервисах компактные и читаемые.

**Меры:** не требуются.

### 1.2 Дублирующийся код
– **Не выявлено**. Логика распределена по отдельным сервисам (AuthService, UserService, PcConfigurationService, ExternalApiService) и mapper-классам. Дублирование отсутствует.

**Меры:** не требуются.

### 1.3 Отсутствие автоматизации (тестов, сборки, развёртывания)
– **Критично**. Папка `src/test/java` полностью пустая (тесты отсутствуют). Сборка через Maven есть, но автоматизированного развёртывания нет (отсутствует Dockerfile и docker-compose.yml).

**Меры:** написать unit-тесты.

### 1.4 Запутанная архитектура и ненужные сложные зависимости
– **Отсутствует**. Архитектура чётко соблюдает шаблон layered architecture (controller → service → repository → entity/dto/mapper). Все зависимости оправданы (Spring Security + JWT, JPA, PostgreSQL, springdoc OpenAPI, MapStruct).

**Меры:** не требуются.

### 1.5 Медленные / неэффективные средства
– **Отсутствует**. Используются стандартные и эффективные инструменты (Spring Boot 3.x + Maven).

**Меры:** не требуются.

### 1.6 Незакоммиченный код / долгоживущие ветки
– **Отсутствует**. В репозитории только ветка `main`, открытых pull request’ов и долгоживущих веток нет.

**Меры:** не требуются.

### 1.7 Отсутствие / несоответствие технической документации
– **Критично**. Файл README.md полностью отсутствует. Есть только Swagger (springdoc), но нет описания запуска, переменных окружения, API и архитектуры проекта.

**Меры:** создать полноценный README.md.

### 1.8 Отсутствие тестовой среды
– **Критично**. Нет отдельного тестового профиля, docker-compose для локальной БД и тест-контейнеров. В `application.properties` используются только продакшен-переменные (`CONFIGURER_POSTGRES_*`).

**Меры:** добавить docker-compose.yml и тестовый профиль.

### 1.9 Неэффективные средства у внешнего сервера
- **Не критично** Для получения данных нужных для одного действия требуется отправить несколько запросов на внешний API.

**Меры:** Поговорить с разработчиков данного API.

## 2 ПЛАН МЕРОПРИЯТИЙ ПО УСТРАНЕНИЮ ТЕХНИЧЕСКОГО ДОЛГА

### 2.1 Мероприятия
1. **Создание README.md** — полное описание проекта, переменных окружения, запуска и Swagger-ссылки. (Высокий приоритет, 1 ч)  
2. **Настройка GitHub Actions** — workflow для Maven build + тесты. (Высокий приоритет, 2 ч)  
3. **Написание базовых тестов** — минимум 10 unit-тестов + 3 integration-теста с @SpringBootTest. (Высокий приоритет, 5 ч)  
4. **Создание тестовой среды** — docker-compose.yml + application-test.properties. (Средний приоритет, 2 ч)  

### 2.2 Оценка плана мероприятий
– **Общий объём работ**: 10 человеко-часов.     
– **Технический долг** после выполнения: снизится с высокого до низкого. Ожидаемая выгода — ускорение разработки нового функционала минимум на 30–40 % за счёт тестов и автоматизации.

## 3 ВЫВОДЫ И КОРРЕКТИРОВКА ПЛАНА РАЗРАБОТКИ

### 3.1 Необходимость устранения долга: частичная, но обязательная
**Полностью устранять долг сейчас не обязательно**, но **критическую часть** (тесты + CI + документация) нужно погасить в ближайшей итерации. Без этого дальнейшая разработка будет сильно замедляться, а добавление нового функционала станет рискованным.

### 3.2 Рекомендуемые критерии
– Код чистый и соответствует принятым стандартам  
– В продакшене (успешный CI/CD)  
– Обновлена документация (README / Swagger)

### 3.3 Корректировка плана разработки
– **Текущая итерация**: выполнение пунктов плана (README + GitHub Actions + базовые тесты).    
– **Следующая итерация**: держать уровень долга на приемлемом уровне для ускорения добавления нового функциоанала.
